# I. 变量

## 1.1 变量声明与赋值的符号使用

经过讨论, 决定新增关键字: `let`

使用 let 进行声明变量 (可以在声明时赋值, 如 `let x: int = 2048`), 且声明变量时必须携带类型标注,

主要是为了降低实现复杂度, 同时明确的变量定义也令代码阅读更加友好

在变量已声明后, 所有的赋值都使用普通等号.

## 1.2 变量二次赋值的类型控制

经过研究, 认为可变类型并不算一个必要的特性, 故决定变量在声明后其类型不再可以更改, 砍掉了
编译期类型的`修改计算`

即:
`
let y: string = "Hello, World!";
y = 4;
`
可以看到此处的变量 y 尝试由原来的 string 转换为 int 类型

我们要求它发生报错, 因为不再允许类型的修改.

注意, 类型可以小变大, 例如 Email 一定是 string, 这里是可以的, 但是不可以让 Email 变成 float, 这是绝对不可行的

# II. 特性, 语法的增减

## 2.1.1 关于重新引入局部 GC

经过长期 Coding 与讨论, 我们决定在现有基础上引入轻量的运行时 GC

我们发现运行时开销、程序安全性与语法简洁性是互斥的, 想要简洁的语法就得有一定程度上的 GC, 想要最快的运行速度而且安全就会引入必不可少的复杂语法拷打程序员

我们的编译期依旧进行逃逸分析与存活分析, 并进行按名追溯, 也就是找到某变量传递链条上最后一个接受赋值的变量, 并研究它的生命周期, 之后做内存释放

对于简单的成环引用, 依旧采用 WSR0 的思路,

而对于生命周期由外部决定的情况, 引入轻量的 GC, 例如库函数中的全局对象, 其生命周期由未知的调用者决定

我们暂时不愿意做太多的条件编译, 并且由于未来一定会出现的线程与进程共享, 为了避免过于复杂的实现与困难的维护, 权衡利弊后所以选择 GC

## 2.1.2 GC 的范围

以下已声明内容依旧由编译期处理:
 - 编译期已知的局部环
 - 编译期已知的未使用变量
 - 编译期可分析的环成员逃逸 (函数中return环成员, 但环成员在外部可分析)

以下内容由 GC 处理
 - 用户输入决定是否可达 | 注意, 虽然编译期可以创造不同的分支, 但是我们并不认为它有多么优雅, 倒不如使用 GC
 - 多线程竞争访问
 - 其余未声明情况

编译期可知的可展平的变量自然是编译期处理, 编译期插入 Drop, 其它的交给 GC 处理

可以预见的, 能展平的变量通常会少于需要 GC 清理的变量, 所以我们决定使用一张简单的表来记录已展平符号, GC 时不会处理表中变量

虽然这与[WSR: 0](./0.md)想要实现的0运行时开销相悖, 但是我们认为将 Rust 复杂的生命周期标注引入 Wind 不是什么好的想法, 我们选择保护开发者的心智而不是开销

## 2.2 关于盒编程与错误处理

### 2.2.1 砍掉盒编程

事实上, 对于盒编程应该是什么样的我们自己也没讨论出一个所以然, 反倒是它把我们搞得一头雾水, 

为了安全而只能传递引用, 拿着个引用去找错误处理器, 错误处理与实际报错代码又不好写到一起, 所以砍掉`tag`和`to`关键字, 砍掉盒编程

### 2.2.2 重新制作错误处理

我们决定砍掉盒编程, 是因为有类似的错误处理中心化语言已经证明这条路并不适合所有人 (例如 Odin 的 Context 机制)

看了一圈, 受检异常太麻烦且容易泛化; try-catch/try-except(t-c)风格处理是隐式控制流, 且实际分支更多; Result 返回值是复杂度的痛苦地狱; Context(Odin)让代码看起来像在正常执行, 实则错误信息已在后台悄然生长, 忘记检查context导致后续逻辑在错误假设下运行; nil(go系)会带来一堆样板代码; C系的数字码不够直观; 代数效应还需要附带证明并且难学, 这几大类错误处理全都在挨骂, 

前人已经走尽了所有处理方式, 我们自认不如先驱者, 我们想不出什么更加新颖的更加好用的错误处理了.

目前有一定可能会选择一种t-c+受检类型+链式调用的变体, 不排除选择其它方案, 还在[讨论中](./error_handler_discussion.md), 不排除使用一种不过分严格(Rust 就是过分严格的代表)的Result的可能

# III. 包导入

## 3.1 包导入的类型

现在主流的解释型语言包导入大体分为三类:
 - 以 Python 和 JavaScript 为主的, 导入时执行模块代码
 - 以 Java 和 Kotlin 为主的, 导入的只是地址别名, 仅用于编译期处理, 而不会直接执行
 - 以 Clojure 为主的, 导入时在编译期执行代码

我们决定采用类似 Java 的包导入模型, 减少不必要的加载时运行也能降低加载耗时

首先让我们回顾一下 Java 在导入时做了什么:

Java: 导入只是 "地址别名"

 - import 在 Java 里完全是编译器层面的, 运行时不存在

写下 `import java.util.ArrayList` 时, JVM 不会:
 - 立刻加载 ArrayList.class 文件(类加载只在第一次真正用到它时才触发)
 - 执行 ArrayList 类里的任何代码，包括 static 代码块(这些只在类初始化时才执行)

`import` 的作用仅仅是: 告诉编译器, 本文件中所有未限定的 ArrayList 都指代 java.util.ArrayList

编译后, 字节码里全是全限定名`java.util.ArrayList`, import 语句完全消失了.
